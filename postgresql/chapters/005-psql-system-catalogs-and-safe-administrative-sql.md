# 005 — psql, System Catalogs and Safe Administrative SQL

[Master plan](../MASTER-PLAN.md) · [Previous chapter](004-build-a-reproducible-postgresql-operations-lab.md) · [Hands-on lab](../labs/005-psql-catalogs-and-safe-sql-lab.md) · [Inspection SQL](../scripts/005-safe-catalog-inspection.sql)

## 1. Operational problem and objectives

An operator can connect successfully yet inspect the wrong database, run a script that continues after failure or leave a transaction open. Administrative reliability starts with predictable client behavior, explicit identity and bounded SQL.

**Audience:** DBRE/SRE only. **Reference:** PostgreSQL 18. Record the actual server and psql versions. **Prerequisite:** the Chapter 004 lab, or an equivalent authorized disposable environment. **Effort:** 60–90 minutes.

After this chapter you should be able to inspect catalogs, distinguish psql commands from server SQL, handle failures in automation, quote variables correctly and verify transaction cleanup.

## 2. Connect deliberately

Use the Chapter 004 primary and its protected password file:

~~~bash
export PGPASSFILE="$PG_LAB_ROOT/credentials.pgpass"
export PGCONNECT_TIMEOUT=5
export PGAPPNAME=chapter005-observer
psql -X -w -v ON_ERROR_STOP=1 \
  -h 127.0.0.1 -p 55432 -U lab_observer -d ops_lab
~~~

-X skips psql startup files, making scripted behavior more predictable. -w prevents password prompting; a missing credential fails instead of waiting unattended. ON_ERROR_STOP makes script errors visible to the caller.

Inside psql, verify the target:

~~~sql
\conninfo
SELECT current_database(), current_user, inet_server_addr(), inet_server_port(),
       pg_is_in_recovery(), current_setting('server_version');
~~~

Database identity alone is insufficient when many environments use the same names. Match endpoint, port, role, version and deployment record before every change.

Local lab loopback settings are not a production TLS policy. Use your approved authenticated and verified connection path in production.

## 3. psql commands versus SQL

| Input | Runs where | Purpose |
|---|---|---|
| SELECT / SHOW / BEGIN | PostgreSQL server | SQL statements |
| backslash-conninfo | psql client | Connection details |
| backslash-d / dt / dn / du | psql client generates SQL | Object, schema and role inspection |
| backslash-i / ir | psql client | Read scripts; ir resolves relative to the current script |
| backslash-pset / x | psql client | Output formatting |
| backslash-r | psql client | Clear unsent query buffer |
| backslash-q | psql client | Exit |
| backslash-copy | psql client | Data transfer through the client |
| backslash-gexec | psql client | Execute SQL generated by query results |

Meta-commands are not server SQL. Use a script file or stdin for combined SQL and meta-commands; do not paste a mixed block into a single -c SQL string.

Review included script files before execution. Generated SQL execution is a change mechanism, not harmless output inspection.

Useful interactive commands:

~~~sql
\pset pager off
\x auto
\timing on
\dn+
\dt public.*
\d+ public.lab_probe
\du
~~~

Timing reports this client's observed command duration; it is not a production latency distribution. Object descriptions and result visibility depend on privileges and versions.

## 4. Catalogs, views and visibility

| Object | Operational question |
|---|---|
| pg_database | What databases exist and who owns them? |
| pg_namespace | What schemas exist? |
| pg_class | What relations exist, of which kinds and owners? |
| pg_roles | What role flags are visible? |
| pg_extension | Which extensions and versions are installed here? |
| pg_settings | What values, units and configuration sources apply? |
| pg_stat_activity | What backends and waits are visible now? |
| information_schema | What portable object metadata is visible to this role? |

Many catalogs are scoped to the current database. Roles and the database catalog have wider scope. A query against pg_class in ops_lab is not an inventory of relations in every database.

Catalog layout can change across major versions. Prefer documented views/functions and version-specific references. Never update catalogs directly to “fix” an object or privilege.

The information schema offers SQL-standard metadata with privilege-based visibility. A monitoring role can see catalog entries without owning or being able to query the corresponding application table. A missing information_schema row does not automatically prove an object is absent.

Inspect relations explicitly:

~~~sql
SELECT n.nspname, c.relname, c.relkind,
       pg_get_userbyid(c.relowner) AS owner
FROM pg_catalog.pg_class AS c
JOIN pg_catalog.pg_namespace AS n ON n.oid=c.relnamespace
WHERE n.nspname='public'
ORDER BY c.relname LIMIT 30;
~~~

relkind distinguishes tables, partitioned tables, views, indexes and other relation types. Do not assume every pg_class row is an ordinary table.

## 5. Schema qualification and safe interpolation

Unqualified names depend on search_path. Qualify important objects and use trusted schemas for administrative routines. The companion script uses pg_catalog for built-in objects and explicitly qualifies information_schema.

psql provides different quoting forms:

| Form | Interpretation | Intended use |
|---|---|---|
| colon-name | Raw substitution | Avoid for untrusted SQL content |
| colon followed by quoted variable name with single quotes | SQL literal quoting | Values |
| colon followed by quoted variable name with double quotes | SQL identifier quoting | Schema/table identifiers |

Example:

~~~sql
\set schema_name public
SELECT :'schema_name' AS requested_schema;
SELECT count(*) FROM :"schema_name".lab_probe;
~~~

Run the table read as lab_app, not the metadata-only observer. These quoting forms do not validate that the chosen target is authorized. A correctly quoted identifier can still name the wrong object.

Use bound parameters in application clients. Do not assemble credentials or untrusted SQL through shell interpolation.

## 6. Bound the session and transaction

For a short metadata review:

~~~sql
BEGIN READ ONLY;
SET LOCAL statement_timeout='5s';
SET LOCAL lock_timeout='1s';
SELECT current_database(), current_user;
ROLLBACK;
~~~

SET LOCAL applies only within the transaction. ROLLBACK ends this inspection transaction and restores local settings.

statement_timeout limits each statement; lock_timeout limits time spent waiting to acquire locks. Make the lock timeout shorter when that distinction is useful. Choose production values based on the operation; these are lab examples.

READ ONLY blocks normal changes to persistent tables, but is not a sandbox for arbitrary SQL, functions, external side effects or psql shell commands. Privilege review and script inspection remain necessary.

A SELECT may consume CPU, memory, I/O or locks. LIMIT reduces returned rows but does not guarantee a cheap plan, particularly when sorting or aggregation precedes it.

Keep diagnostic transactions short. If an interactive statement errors inside a transaction, normally issue ROLLBACK before proceeding. Do not abandon the session idle in transaction.

## 7. Reliable script execution and output

Run the bounded inventory script:

~~~bash
mkdir -p evidence/chapter005
psql -X -w -v ON_ERROR_STOP=1 \
  -h 127.0.0.1 -p 55432 -U lab_observer -d ops_lab \
  -v schema_name=public \
  -f postgresql/scripts/005-safe-catalog-inspection.sql \
  > evidence/chapter005/catalogs.txt \
  2> evidence/chapter005/catalogs-errors.txt
~~~

Check the exit status immediately. A created output file can be partial and is not proof of success.

psql distinguishes normal completion, client/fatal errors, lost connection in noninteractive mode and script errors with ON_ERROR_STOP. Treat any nonzero status as failure; retain stderr and the target identity.

ON_ERROR_STOP does not undo commands committed earlier in a script. Use an explicit transaction for a reviewed set of compatible changes when atomicity is required. Some operations cannot run inside a transaction block; do not add --single-transaction blindly.

For a single metadata dataset, export CSV:

~~~bash
psql -X -w --csv -v ON_ERROR_STOP=1 \
  -h 127.0.0.1 -p 55432 -U lab_observer -d ops_lab \
  -c "SELECT extname,extversion FROM pg_catalog.pg_extension ORDER BY extname;" \
  > evidence/chapter005/extensions.csv
~~~

Do not concatenate multiple unrelated result sets and call them one CSV table. Client-side export writes on the client host; server-side file operations have different permissions and paths.

## 8. Production change discipline

Before executing administrative SQL, record identity, intended effect, privileges, expected row/object count, lock risk, timeout, rollback boundary and verification query.

Use the least-privileged suitable role. Monitoring credentials should not routinely cancel sessions, change roles, restart instances or access server files.

Do not run EXPLAIN ANALYZE on an arbitrary write under the assumption it only explains it: it executes the statement. A later chapter covers plan inspection and side-effect boundaries.

For an incident, start with metadata evidence and business impact. Cancelling or terminating a backend requires target ownership and transaction-impact review. Those operations are outside this chapter's lab.

## 9. Troubleshooting and acceptance

| Symptom | Safe interpretation/action |
|---|---|
| Backslash command fails in a driver | It belongs to psql, not SQL |
| Script continues after SQL error | Enable ON_ERROR_STOP and inspect caller status |
| Error leaves interactive transaction unusable | ROLLBACK, then reassess |
| Catalog and information_schema differ | Review role visibility and object scope |
| Table exists but observer cannot SELECT | Catalog visibility is not data access |
| Unexpected object selected | Verify schema qualification and search_path |
| Output exists but command failed | Treat file as partial; inspect stderr |
| Generated statements look correct | Review each before any execution |

Complete the lab: inventory the target, demonstrate quoting, read-only rejection, rollback and script failure handling. Verification remains separate from authorship.

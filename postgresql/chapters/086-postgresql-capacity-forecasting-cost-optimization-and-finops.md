# Chapter 086 — PostgreSQL Capacity Forecasting, Cost Optimization and FinOps

**Track:** PostgreSQL DBRE/SRE | **Baseline:** PostgreSQL 18 | **Status:** Authored; runtime validation pending

## 1. Mission

Build an evidence-driven PostgreSQL capacity and cost forecast covering compute, memory, disk, IOPS, throughput, WAL, HA, backups and cloud operating costs. Translate forecasts into defensible rightsizing decisions with explicit reliability gates.

## 2. Capacity model

```text
Business demand / tenants / queries / ingest
                |
       Workload profile and growth
                |
 CPU + memory + connections + disk + IOPS + network
                |
 Replicas + WAL archive + backups + recovery capacity
                |
 Cost forecast + SLO/RPO/RTO + decision thresholds
```

Separate **allocated capacity**, **used capacity**, **peak demand**, **sustained demand** and **growth rate**. A single daily average hides bursts and cannot justify a production downsize.

## 3. Inventory and baselines

Collect 30–90 days where available, including weekly/seasonal peaks and maintenance windows. Track:

| Domain | Required measurements | Source |
|---|---|---|
| CPU | Utilization, saturation, steal/throttling, run queue | Host/cloud metrics |
| Memory | RSS, page cache, swap, OOM, PostgreSQL settings | OS/cloud + SQL |
| Connections | Active/idle sessions, pool queue, max_connections | pg_stat_activity + pooler |
| Storage | Allocated, used, table/index/TOAST, temp, free space | SQL + filesystem/cloud |
| Disk I/O | IOPS, throughput, latency, queue depth | Host/cloud metrics |
| WAL | Generated bytes/time, archive success, slot retention | pg_stat_wal, archiver, slots |
| Replication | Lag bytes/time, slot health, failover headroom | Primary/standby metrics |
| Backups | Full/incremental/WAL size, retention, restore time | Backup system |
| Cost | Compute, storage, IOPS, network, snapshots, backup, licenses | Provider billing |

PostgreSQL SQL views do **not** directly expose cloud volume provisioned IOPS, physical disk latency or instance prices. Collect those externally.

## 4. Read-only inspection

Use [086 capacity SQL](../labs/sql/086-capacity-inspect.sql) on each database/cluster node. Key queries:

```sql
SELECT pg_database_size(current_database()) AS database_bytes;
SELECT datname,numbackends,xact_commit,xact_rollback,
       temp_bytes,blks_read,blks_hit
FROM pg_stat_database ORDER BY datname;
SELECT pg_current_wal_lsn() AS current_lsn
WHERE NOT pg_is_in_recovery();
```

The WAL LSN query is for primaries; a standby requires replay/receive LSNs. `pg_stat_wal.wal_bytes` is cumulative and needs two timestamped samples with reset detection for a rate. SQL statistics can be reset; account for counter discontinuities.

## 5. Forecasting methodology

For a measured quantity `S0` and average monthly growth `g`:

```text
Linear:      S(t) = S0 + (absolute_growth_per_month * t)
Compounded:  S(t) = S0 * (1 + g)^t
Usable limit = allocated_capacity * (1 - reserved_headroom_fraction)
Time-to-limit = first t for which forecast S(t) >= usable limit
```

Choose linear vs compound based on observed growth, not convenience. Model low/base/high scenarios, ingest changes, retention policy and step-function events (new tenants, backfills, migrations).

**Illustrative only:** 2 TiB used, 8% monthly compound growth and 20% reserved headroom on 4 TiB allocated gives 3.2 TiB usable. Forecast reaches the usable threshold around month 7 (2 × 1.08^7 ≈ 3.43 TiB). Real planning must include free-space requirements for vacuum, reindex, replication and restore.

## 6. CPU and memory rightsizing

Estimate demand from peak concurrency, query CPU time, batch schedules and connection pooling. `max_connections` is a ceiling, not a throughput target. Reducing instance memory can shrink effective OS page cache and worsen disk I/O even if `shared_buffers` is unchanged.

Check memory amplification: per-session `work_mem` can be used by multiple sort/hash nodes and parallel workers; never estimate total memory as `work_mem × max_connections` alone. Account for shared_buffers, maintenance_work_mem, autovacuum workers, WAL buffers, background workers, OS cache and safety margin.

## 7. Storage, WAL and IOPS

Plan separate capacities for live data, indexes, TOAST, dead tuples/bloat, temp files, WAL, replication slots, backups and maintenance scratch space. Monitor p95/p99 disk latency and I/O queue depth alongside query latency. For storage autoscaling, verify maximum volume size, IOPS/throughput ceilings, provider limits and scaling lead time.

```text
WAL retention exposure ≈ WAL generation rate × consumer outage duration
Total WAL headroom must cover slots, archiving delay, burst traffic and recovery margin
```

A stalled logical slot can retain WAL and exhaust disk. Do not drop production slots solely to reduce cost without CDC/data-loss analysis.

## 8. HA and DR cost

Total production cost includes standby instances, cross-zone/cross-region replication traffic, storage duplication, snapshots, archived WAL, backup retrieval, test restores, failover capacity and monitoring. A cheap standby that cannot absorb primary load does not meet HA acceptance. Cost optimization must preserve approved RPO/RTO and recovery test frequency.

## 9. FinOps levers

| Lever | Potential saving | Reliability check |
|---|---|---|
| Right-size compute | Lower instance-hour cost | Peak CPU/memory and app SLO |
| Connection pooling | Reduce backend overhead | Pool queue, transactions, session semantics |
| Storage tier optimization | Lower GB-month / IOPS charges | p95 latency, burst and throughput limits |
| Retention/partition lifecycle | Reduce live storage | Legal hold, restore and downstream consumers |
| Index review | Reduce write amplification/storage | Query plan and workload regression tests |
| Backup lifecycle | Lower backup storage | Immutable recovery copies and restore acceptance |
| Scheduled nonprod shutdown | Reduce idle compute | Environment dependencies and startup readiness |
| Reserved/committed capacity | Lower unit cost | Forecast confidence and contract flexibility |

Never optimize by disabling backups, replicas, TLS, audit logging or essential monitoring without a formally approved risk decision.

## 10. Cost model and scenario comparison

```text
Monthly cost =
 compute hours × unit compute rate
 + provisioned storage GiB-month × unit rate
 + provisioned IOPS/throughput charges
 + backup/snapshot/WAL archive storage
 + cross-zone/region data transfer
 + monitoring/support/license costs
```

Prices are cloud-, region-, service-, tier- and contract-specific. Record billing source/date, currency, assumptions, utilization and uncertainty. Distinguish marginal savings from one-time migration effort and outage risk. Use [086 cost model CSV](../labs/finops/086-capacity-cost-model.csv) to capture scenarios; values are placeholders until real billing inputs are supplied.

## 11. Capacity incident runbook

**Detect:** identify exhausted resource and rate of change, confirm application impact and estimate time-to-limit.

**Stabilize:** stop nonessential bulk jobs, protect backups and replication, scale approved capacity, manage connections and long transactions. Do not perform risky cleanup or drop slots blindly.

**Diagnose:** correlate query load, WAL/slot retention, storage I/O, autovacuum, temp files and growth events.

**Recover:** verify disk headroom, query latency, replica lag, backup archive and application SLO.

**Prevent:** update forecast, thresholds, retention policy, capacity reservations and scaling lead time.

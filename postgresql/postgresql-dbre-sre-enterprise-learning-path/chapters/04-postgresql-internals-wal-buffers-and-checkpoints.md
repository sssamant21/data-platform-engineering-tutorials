## 3. Architecture: what happens on INSERT or UPDATE?

```text
Application / psql
       |
       v
PostgreSQL backend (SQL parsing, plan, execution)
       |
       +--> shared_buffers: changed data/index pages become dirty
       |
       +--> WAL buffers: records describing changes
                      |
                      v
                WAL segment files in pg_wal/
                      |
                WAL flush on commit*
                      |
          COMMIT acknowledgement to client
                      |
             later/independently
                      v
  background writer + checkpointer + client backends
                      |
               data/index files
```

*The exact commit acknowledgement and durability semantics depend on settings such as `synchronous_commit` and `fsync`, storage behavior and replication configuration. The diagram describes the conventional local-durability path with safe defaults, not every possible configuration.*

**WAL-before-data rule:** relevant WAL records must reach durable storage before changed data pages can be written to permanent storage. That lets crash recovery redo committed changes that had not yet reached data files. WAL is primarily sequential I/O; dirty data-page writes can be scattered across table and index files. <https://www.postgresql.org/docs/18/wal-intro.html>

### Components and responsibilities

| Component | Function | Common misconception |
|---|---|---|
| `shared_buffers` | PostgreSQL-managed cache for table/index pages | Not identical to OS page cache or total RAM used |
| WAL buffers (`wal_buffers`) | Memory staging for WAL records | Not a replacement for WAL files or durability |
| `pg_wal/` | Local WAL segment files for recovery/replication/archiving | Not an independently recoverable backup |
| WAL writer | Helps write WAL buffers to WAL files | Does not guarantee every commit waits for it |
| Background writer | Writes some dirty shared buffers ahead of demand | Does not perform checkpoints |
| Checkpointer | Coordinates checkpoint writes and synchronization | Does not make every transaction commit wait for a checkpoint |
| Backend | Executes SQL; may also perform buffer writes and WAL flushing | I/O is not exclusively handled by background processes |
| OS/storage | Page cache and durable media | Storage cache behavior affects real durability |

## 4. WAL, LSN and crash recovery

**Write-Ahead Log (WAL)** records changes needed to recover database pages. A WAL **Log Sequence Number (LSN)** identifies a position in the WAL byte stream. On a writable primary, `pg_current_wal_lsn()` exposes the current insert position, and `pg_wal_lsn_diff(end, start)` measures byte-distance between two LSNs.

For a quiet, isolated lab:

```sql
SELECT pg_current_wal_lsn();
SELECT wal_records, wal_fpi, wal_bytes, wal_buffers_full
FROM pg_stat_wal;
```

These are **cluster-wide** values. The LSN delta includes concurrent WAL generated by other databases, so it is not a precise per-table or per-transaction bill. `pg_stat_wal` is cumulative and statistics may update asynchronously.

### Crash recovery versus backup

After a crash, PostgreSQL replays WAL starting from an appropriate checkpoint REDO location to restore consistency. This is **not** the same as restoring deleted data from an independent backup. Point-in-time recovery (PITR) requires a valid physical base backup and a continuous, verified WAL archive covering the desired recovery window. Merely having files in `pg_wal` does not establish PITR readiness.

### Full-page images (FPI)

With `full_page_writes=on`, the first change to a data page after a checkpoint can include a full-page image in WAL to protect against torn pages. Consequently, more frequent checkpoints can increase WAL volume and write I/O. Compression and workload patterns affect observed WAL volume; do not extrapolate from one small lab.

## 5. Checkpoints and buffer management

A checkpoint establishes a recovery reference and coordinates writing dirty buffers to data files. PostgreSQL normally schedules checkpoints based on `checkpoint_timeout` or WAL pressure relative to `max_wal_size`. A checkpoint may be skipped when no WAL has been written since the previous checkpoint.

```sql
SHOW shared_buffers;
SHOW wal_buffers;
SHOW checkpoint_timeout;
SHOW max_wal_size;
SHOW checkpoint_completion_target;
SHOW full_page_writes;
SHOW fsync;
SHOW synchronous_commit;
```

**Operational cautions:**
- `max_wal_size` is a soft target for checkpoint behavior, **not a hard cap** on disk usage in `pg_wal`.
- `checkpoint_completion_target` spreads checkpoint writes to reduce bursts; changing it without evidence can worsen I/O.
- Do **not** disable `fsync` or `full_page_writes` to mask latency. Those settings affect durability and corruption risk.
- Do **not** force `CHECKPOINT` for this introductory lab: it can create unnecessary I/O and alter observations.
- In managed services, some settings and OS-level metrics may be unavailable or provider-controlled.

### What makes WAL disk usage grow?

Potential causes include high write volume, bulk loads, frequent full-page images, checkpoint/recycling policy, lagging physical or logical replication slots, archive failures, and backup/recovery requirements. Investigate **which** retention constraint applies before changing configuration. Never manually delete files from `pg_wal`.

## 6. PostgreSQL 17 monitoring surfaces

PostgreSQL 17 exposes distinct statistics for WAL, checkpointing, background writer and general I/O.

| View / function | Useful signals | Interpretation limit |
|---|---|---|
| `pg_stat_wal` | `wal_bytes`, `wal_records`, `wal_fpi`, `wal_buffers_full` | Cluster-wide, cumulative since reset |
| `pg_stat_checkpointer` | `num_timed`, `num_requested`, `buffers_written`, `write_time`, `sync_time` | Counters can remain unchanged during a short lab |
| `pg_stat_bgwriter` | `buffers_clean`, `maxwritten_clean`, `buffers_alloc` | Separate from checkpointer counters in PostgreSQL 17 |
| `pg_stat_io` | I/O by backend type, object and context | Not all operations/paths are counted; some cells are NULL |
| `pg_stat_database` | `blks_hit`, `blks_read` | Cache hit ratio is not a complete latency measure |
| `pg_current_wal_lsn()` | Current WAL insert position | Primary-only observation; not a disk-space metric |
| `pg_replication_slots` | Slot activity and retained restart LSN | Empty in a standalone lab; production interpretation needs context |

**Version warning:** examples in older tutorials may read checkpoint fields from `pg_stat_bgwriter`. In PostgreSQL **17**, use `pg_stat_checkpointer` for checkpoint counts and timing.

```sql
SELECT wal_records, wal_fpi, wal_bytes, wal_buffers_full, stats_reset
FROM pg_stat_wal;

SELECT num_timed, num_requested, buffers_written,
       write_time, sync_time, stats_reset
FROM pg_stat_checkpointer;

SELECT backend_type, object, context, reads, writes, hits, evictions
FROM pg_stat_io
WHERE object = 'relation'
ORDER BY backend_type, context
LIMIT 20;
```

The timing columns of WAL/I/O views depend on `track_wal_io_timing` / `track_io_timing`; zeros do **not** necessarily prove fast storage.

## 8. Incident walkthrough: WAL disk alert

**Scenario:** a production PostgreSQL primary has a rapidly growing `pg_wal` directory, rising write latency and a replica that is no longer catching up.

Recommended investigation order:

1. Confirm cluster identity, version, role (primary/standby), alert scope and available disk space.
2. Quantify WAL generation rate over time (LSN delta, `pg_stat_wal` deltas, exporter metrics).
3. Check replication slot status and lag; identify any inactive slots retaining WAL.
4. Check archiver success/failure metrics and retention requirements.
5. Review checkpoint frequency, write/sync time, storage latency and workload changes.
6. Coordinate with DBRE, application and platform owners on the root cause and mitigation.
7. Preserve backups, required WAL and replication correctness; validate recovery posture after changes.

**Unsafe shortcuts:** deleting `pg_wal` files, dropping a replication slot without confirming consumer recovery, disabling `fsync`, or changing WAL retention blindly.

### Application/architecture questions

- How much WAL does the workload produce during peak ingestion?
- Are there read replicas, logical decoding consumers, CDC connectors or PITR requirements?
- What are the approved RPO/RTO and archive retention policies?
- Which party owns disk capacity, alerting, slot lifecycle and archiving across bare metal, AWS RDS and Kubernetes?
- How do we prove a mitigation did not damage recovery or replication?

## 10. Troubleshooting

| Symptom | Explanation | Safe response |
|---|---|---|
| `pg_stat_checkpointer` missing | Connected to an older PostgreSQL version | Confirm `server_version_num`; use version-specific docs |
| `pg_current_wal_lsn()` returns NULL | Server is in recovery | Confirm `pg_is_in_recovery()`; do not treat as primary |
| No checkpoint delta | Short exercise, scheduled interval not reached | Record unchanged counters; do not force checkpoint |
| I/O time columns zero | Timing instrumentation disabled or no activity | Check `track_io_timing` and `track_wal_io_timing` |
| LSN delta differs from `wal_bytes` delta | Different measurement semantics, asynchronous stats, other workload | Explain differences rather than forcing agreement |
| `pg_wal` remains large | Recycling, slots, archiving or checkpoint policy | Investigate retention constraints; never delete WAL manually |
| Permission denied on stats | Insufficient role privileges | Use an approved monitoring role and least-privilege access |

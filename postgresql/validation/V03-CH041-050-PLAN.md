## V03-A — Chapter 004 / Chapter 047 capacity prerequisite

The Chapter 004 isolated PostgreSQL 18 setup previously used `max_replication_slots = 0`, which made Chapter 047 physical slot creation impossible. The disposable topology now sets `max_replication_slots = 4` and `max_slot_wal_keep_size = '256MB'`. Both settings are copied to the standbys; `004-operations-lab.sh verify` checks all three endpoints before its write probe.

The Chapter 047 slot-creation gate now rejects insufficient/exhausted slot capacity and absent, unlimited, or oversized (`>512MB`) slot-retention settings. The existing exact database, role, loopback port, PG18 version, absolute PGDATA pattern, system ID and `047-CREATE-SLOT` token checks remain mandatory. The static contract suite `test_v02d_ch041_050.py` includes a new regression covering configuration and guards.

**Important:** `max_replication_slots` changes require a restart. Create a **fresh**, unshared Chapter 004 lab; do not silently reconfigure an existing or production cluster. `max_slot_wal_keep_size` is applied at checkpoints, not a hard immediate cap on `pg_wal` disk occupancy. Large WAL workloads or a stalled consumer can still cause data loss/invalidation or disk pressure.

### Local, authorized PostgreSQL 18 verification

1. As an unprivileged OS user, run `bash postgresql/scripts/004-operations-lab.sh setup` on an isolated machine with sufficient disk. Export the printed `PG_LAB_ROOT`.
2. Run `bash postgresql/scripts/004-operations-lab.sh verify`, preserving command exit codes and redacted logs.
3. Check `SHOW max_replication_slots;`, `SHOW max_slot_wal_keep_size;`, `SELECT system_identifier FROM pg_control_system();`, and `SELECT slot_name, active, restart_lsn, wal_status, safe_wal_size FROM pg_replication_slots;` on the disposable primary at loopback port 55432.
4. Capture free disk space and the data directory identity independently. Do not infer the system ID or substitute a shared endpoint.
5. Only after negative tests pass, follow Chapter 047's existing one-time stage-token commands. Inspect any partial state before attempting cleanup.

## V03-B — Negative preflight gate (must fail closed)

| Exercise | Expected result | Required evidence |
|---|---|---|
| Missing / wrong `expected_system_id` | `psql` nonzero; no slot created | Exit status, read-only slot inventory |
| Wrong `047-CREATE-SLOT` token | Nonzero; no slot created | Exit status |
| Target standby / wrong port / wrong role | Nonzero; no slot created | Endpoint, role, exit status |
| Slot already exists or slots exhausted | Nonzero; existing slots untouched | Before/after inventory |
| `max_replication_slots=0` or unbounded slot retention | Refused by stage guard | Lab-specific isolated negative fixture; no shared-cluster settings |
| Repeat `047-GENERATE-WAL` or `048-WORKLOAD` | Nonzero; fixture unchanged | Counts, hashes, exit status |
| Wrong `047-DROP`/`048-DROP` token or altered fixture | Nonzero; no unauthorized object changes | Schema and slot inventory |
| Active Chapter 047 slot cleanup | Nonzero; active consumer preserved | Slot active state, exit status |
| Chapter 045 recovery verification on wrong PGDATA | Nonzero; restore rejected | Command, exit status, endpoint identity |

Never run potentially destructive negative cases on production or shared staging. Check that each refused step leaves state unchanged, not merely that a refusal string appears.

## V03-D — Acceptance and certification boundaries

- **Static acceptance:** Python regression tests and SQL/Markdown parsers should pass on the code-bearing branch. These checks do not prove runtime behavior.
- **Live acceptance:** requires an approved disposable PG18 environment and preserved logs, exit codes, system identifiers, backups, WAL/timeline evidence, state invariants, and UTC timestamps.
- **Promotion safety:** if independent old-primary fencing is unproven, **STOP**; do not promote. Do not run actual `pg_rewind` without target backup, clean shutdown, source/target ancestry checks, approval and rejoin plan.
- **PITR safety:** recover to a separate instance, verify the approved point between good and bad commits, and compare business invariants. Verify recovery target before routing traffic.
- **Enterprise certification:** remains **NOT CERTIFIED** until independent DBRE/security review and the complete mandatory HA/DR scorecard pass.

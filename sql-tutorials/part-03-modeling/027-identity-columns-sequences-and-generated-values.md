## Concepts and portable SQL (5–15 minutes)

A **surrogate key** identifies a row without carrying business meaning. An **identity column** requests automatically generated values when inserting rows; in PostgreSQL it is backed by an implicit sequence. A **sequence** is a counter object that can supply values to multiple expressions. A **generated column** derives its value from other columns and is different from an identity: it is not an independent counter.

The SQL-standard-style identity syntax is:

```sql
CREATE TABLE orders (
  order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_code VARCHAR(20) NOT NULL UNIQUE
);
```

`GENERATED ALWAYS AS IDENTITY` ordinarily rejects an explicitly supplied ID; PostgreSQL can allow one using `OVERRIDING SYSTEM VALUE` in INSERT. `GENERATED BY DEFAULT AS IDENTITY` permits explicit IDs. An identity declaration **does not itself enforce uniqueness**; add `PRIMARY KEY` or `UNIQUE`. PostgreSQL identity columns are implicitly NOT NULL.

Sequence numbers are **not gapless**: rollbacks, failed inserts, caching, and concurrent activity may consume numbers. PostgreSQL `nextval()` is not rolled back. Do not use sequence values as legal invoice numbering, ordering guarantees, or a substitute for `ORDER BY`. Use stable business keys and idempotency checks for deduplication.

A PostgreSQL-specific computed example:

```sql
CREATE TABLE order_lines (
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  unit_price NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0),
  line_total NUMERIC(12,2)
    GENERATED ALWAYS AS (quantity * unit_price) STORED
);
```

The expression is computed by the database. PostgreSQL generated expressions must satisfy immutability and other restrictions; they cannot depend on other rows or volatile functions. PostgreSQL 18 also supports virtual generated columns, with different restrictions; the lab uses **STORED** for clarity. A generated column cannot be freely assigned an arbitrary value in an INSERT.

**Dialect differences:** SQL Server uses `IDENTITY(seed, increment)` and computed columns; MySQL uses `AUTO_INCREMENT`; Oracle supports identity columns and sequences; SQLite uses integer rowid behavior; Snowflake has sequences and identity/autoincrement behavior; BigQuery does not offer equivalent ordinary OLTP identity semantics. Verify the exact engine/version, concurrency and migration semantics before porting.

## Worked example and expected results (15–30 minutes)

The lab creates a temporary `ch027_orders` table with `GENERATED ALWAYS AS IDENTITY (START WITH 100)`. Two inserts omit the ID. Expected IDs: **100 and 101**. An explicit ID of 999 is deliberately rejected with SQLSTATE **428C9** (`generated_always`), while an explicit override with `OVERRIDING SYSTEM VALUE` succeeds for 999. The next generated ID remains **102**: manually overriding a value does not automatically advance the underlying sequence.

A second temporary table uses `BY DEFAULT` and accepts an explicit ID of 500; its next automatically generated ID is **1**, independently of the explicit value. This is a potential collision risk if applications insert IDs manually. The lab verifies that behavior and tests a duplicate-key rejection.

A third temporary table computes line totals from synthetic quantities and prices:

| order_id | quantity | unit_price | expected line_total |
|---:|---:|---:|---:|
| 100 | 2 | 12.50 | 25.00 |
| 101 | 3 | 7.25 | 21.75 |

Expected total: **46.75**. This is a computed value, not a sequence or a default. Explicitly supplied generated values are rejected except for supported `DEFAULT` behavior.

## DBRE/SRE and data engineering considerations (50–55 minutes)

| Symptom | Likely cause | Safe response |
|---|---|---|
| `428C9` on explicit identity value | ALWAYS identity rejects direct override | Confirm whether explicit import is justified; use approved override only in isolated migration |
| `23505` duplicate ID | Sequence state and manually imported IDs conflict | Inspect identity metadata, keys and sequence state; reconcile under change control |
| Missing sequence numbers | Rollback, concurrency, failed insert, cache | Treat gaps as normal; never reseed to fill gaps |
| Generated-column insert fails | Attempted explicit computed value | Omit the generated column from INSERT |
| Sequence near exhaustion | Narrow integer type or long-running growth | Forecast capacity; plan BIGINT migration and application compatibility |
| Wrong business record joined | Surrogate ID used across systems without mapping | Use stable source-system business identifiers and reconciliation |

**Production guardrails:** Do not run `setval`, `ALTER SEQUENCE RESTART`, `TRUNCATE ... RESTART IDENTITY`, or bulk backfills without approved maintenance and ownership review. These may collide with concurrent writers, replication, CDC, or downstream consumers. Sequence allocation is not a commit-order timestamp. During imports, reconcile maximum stored IDs and the actual sequence state under a controlled write boundary, then test the next allocation before enabling writers. Monitor sequence headroom and key uniqueness separately.

## Review questions and answers (55–60 minutes)

1. **Is an identity column automatically unique?** No; enforce uniqueness with PRIMARY KEY or UNIQUE.
2. **What differs between ALWAYS and BY DEFAULT?** ALWAYS normally rejects explicit values; BY DEFAULT accepts them.
3. **Does an override to 999 advance the next generated ID?** No; it does not automatically synchronize the sequence.
4. **Are sequence values gapless or transactional?** No; `nextval` allocations are not rolled back.
5. **What is a computed generated column?** A database-maintained expression derived from other row columns.
6. **Can generated expressions reference another row?** Not in PostgreSQL generated column expressions.
7. **What is needed for runtime validation?** Actual isolated PostgreSQL 18 execution, passing assertions, full logs and cleanup evidence.
8. **Why use synthetic data?** It permits safe experimentation without exposing customer or operational records.
